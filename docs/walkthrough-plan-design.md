# План код-ревью (Walkthrough) - дизайн фичи

Фича для связки "revu + форк difit": агент генерирует план прохода по коду ревью (в духе CodeRabbit walkthrough), пользователь листает его страницами в UI difit, видит живые сниппеты кода/диффа, проваливается в полный дифф и комментирует - прямо из плана или из диффа. Интеграция в общую архитектуру - в `difit-wrapper-design.md` (он главнее при расхождениях).

## 1. Архитектурное размещение

- Реализация - в **форке difit**, изменения максимально изолированы: новый код в отдельных директориях, в оригинальные файлы только точечные точки подключения (mount, роут, регистрация), чтобы merge с upstream проходил с минимумом конфликтов.
- **Обертка (revu) - единственная точка запуска и обновления difit.** Вся логика персистентности, валидации между запусками и агентских команд живет в ней.
- difit в этой схеме - **stateless рендер-мишень**: получает план в runtime, рендерит, ничего не решает про актуальность и не хранит план между запусками.

## 2. UI: режим Walkthrough

- Отдельный **полноэкранный режим** внутри SPA difit с переключением "план <-> дифф". Не двухпанельная раскладка.
- Если план есть - при открытии пользователь попадает **сразу в план**. Позиция (страница + скролл) в MVP не персистится: план всегда открывается с первой страницы, позиция живет только в стейте открытой вкладки. Если плана нет - поведение difit не меняется, фича не оставляет следов в UI.
- Страницы отображаются в заданной последовательности, навигация: вперед/назад, оглавление, переходы по ссылкам `#page:` между страницами.
- Drill-down: у каждого сниппета кнопка "открыть в полном диффе" - переключает режим и скроллит дифф к тем же файлу/строкам (механика скролла к позиции переиспользуется из CommentsListModal / findCommentPosition). Возврат в план - с сохранением позиции вкладки.

## 3. Формат плана (schemaVersion 1)

Синтаксис v1 зафиксирован; эволюция возможна по мере обкатки со скиллом агента, совместимость контролируется полем `schemaVersion`.

- HTML от агента не принимается. Голые MD-файлы без структуры не принимаются.
- План - **JSON-конверт**, тело страниц - Markdown:

```json
{
  "schemaVersion": 1,
  "title": "Review: добавление rate limiter",
  "pages": [
    { "id": "transport", "title": "1. Транспортный слой", "body": "markdown..." },
    { "id": "usecase", "title": "2. Use case", "body": "markdown..." }
  ]
}
```

- `id` страницы - slug: `^[a-z0-9][a-z0-9_-]*$`, до 64 символов, уникален в пределах плана.
- Спецэлементы в `body`:
  - **Сниппет кода** - fenced-блок с YAML-телом (парсится js-yaml - он уже зависимость difit; строгий режим):

    ````
    ```difit-ref
    file: src/api/limiter.ts
    lines: 10-25
    side: new
    ```
    ````

    Поля: `file` - путь от корня репозитория (обязателен; YAML-квотинг закрывает пути с пробелами и спецсимволами), `lines` - `"N"` или `"N-M"` (обязателен; один диапазон на блок - для нескольких диапазонов несколько блоков), `side` - `old`|`new` (опционален, по умолчанию `new`; для неизмененных файлов допустима ссылка без side). Неизвестные ключи - ошибка валидации. Текст кода агент в план не вкладывает никогда.
  - **Ссылка на страницу плана** - обычная md-ссылка `[текст](#page:transport)`.
- Формат **не знает о слоях**: слои (transport -> use case -> repository и т.п.) - это содержимое, которое агент кладет в заголовки и порядок страниц. Стиль нарезки прохода - зона скилла агента, не схемы данных.

### Валидация (жесткая, на входе)

Единый переиспользуемый модуль валидации - пакет воркспейса `plan-schema` (используется dry-run командой `revu plan validate` и сервером difit как страховкой при `POST /api/walkthrough`). Проверяется: схема конверта, уникальность и формат id страниц, разрешимость всех `#page:`-ссылок, синтаксис каждого `difit-ref` (YAML, состав ключей, формат lines), существование каждого файла из `difit-ref` в диффе (или в репозитории для blob-ссылок на неизмененный код), попадание диапазонов строк в реальные границы. Невалидный план отклоняется целиком с машиночитаемым списком ошибок - агент читает их и чинит план сам.

## 4. Рендер сниппетов

- Страницы рендерятся через react-markdown (переиспользование подхода CommentBodyRenderer) с кастомными компонентами: fenced-блок `difit-ref` мапится на новый компонент `WalkthroughSnippet`, ссылки `#page:` перехватываются навигацией плана.
- `WalkthroughSnippet`: находит файл в загруженном `diffData`, вырезает поддиапазон строк из hunk'ов (утилита "slice chunk по old/new строкам") и рендерит существующим `DiffChunk` / `SideBySideDiffChunk`. Бесплатно: Prism-подсветка, word-level diff, split/unified, полное визуальное совпадение с полным диффом.
- Код вне диффа (неизмененные файлы, контекст за пределами hunk'ов) - через существующую машинерию `useExpandedLines` (`/api/line-count` + `/api/blob`): синтезируется chunk из context-строк.
- Walkthrough-режим монтируется внутри App, чтобы работали провайдеры WordHighlightContext / FileLevelTokensContext.

## 5. Комментарии

- Комментировать можно **прямо в сниппете на странице плана**. Хендлеры комментариев прокидываются в DiffChunk через пропсы (как в обычном диффе); якорь треда (filePath + side + line) не зависит от места создания - тред попадает в общее хранилище и виден и в плане, и в полном диффе.
- Существующие треды, чей якорь попадает в диапазон сниппета, отображаются в сниппете - чтобы пользователь не дублировал замечания.

## 6. Хранение и источник правды

- **Источник правды - персистентное хранилище демона revu** (`~/.revu/state/.../plan.json`), в разрезе ветки/задачи, рядом с комментариями. Серверная память difit умирает с процессом - план в ней не живет.
- При установке плана обертка сохраняет **хэш содержимого каждого сниппета** (реального кода по ссылке на момент установки).
- Доставка в difit - **только runtime**: демон делает `POST /api/walkthrough` сразу после подъема инстанса и после каждого `plan set`; клиент забирает план через `GET /api/walkthrough`; обновление на лету - SSE-событие `walkthroughChanged` в существующий канал `/api/watch`. Стартового флага предзагрузки нет.

## 7. Модель устаревания

Два дополняющих механизма:

1. **Между запусками - обертка.** При каждом запуске пересчитывает хэши сниппетов, сравнивает с сохраненными; расхождения помечает stale-флагом на уровне отдельного сниппета при заливке плана в difit и формирует машиночитаемый отчет вида "страница `usecase`, сниппет #2 (src/api/limiter.ts:10-25) устарел". difit решения не принимает - только рендерит флаг.
2. **Внутри сессии - клиент.** Ревалидация ссылок текущей страницы при получении нового плана (`plan set` на лету); неразрешимые рендерятся заглушкой. Live-reload в managed-режиме не бывает - дифф внутри сессии неизменен, так что это только защита от рассинхрона плана с диффом.

UI: stale/сломанный сниппет - заглушка с путем/строками, пометкой "код изменился" и кнопкой перехода в полный дифф; план продолжает работать (мягкая деградация, никакой жесткой инвалидации целиком). В шапке плана - баннер "дифф изменился с момента генерации плана, N ссылок устарело".

Перегенерация плана - зона обертки/агента, не difit.

## 8. Агентский интерфейс (команды revu)

Все команды работают **без запущенного difit** - против хранилища демона и git напрямую. Если инстанс запущен, `plan set` дополнительно пушит план в него.

- `revu plan validate <file>` - dry-run: схема + достижимость ссылок + границы строк, без запуска difit и без записи. Агент итерирует план до чистой валидации.
- `revu plan get` - текущий план из хранилища со свежерассчитанными stale-флагами по сниппетам.
- `revu plan set` - валидация, запись в хранилище, пересчет и сохранение хэшей сниппетов, push в живой инстанс при наличии.
- `revu plan check` - только проверка актуальности кодовой части: хэши из хранилища против текущего git; отчет "какой сниппет в каком пункте плана устарел", без передачи самого плана.

Сценарии агента: проверить план по просьбе пользователя (`check`); при неактуальности - запросить весь план с флагами (`get`); сгенерировать новый по текущему коду и установить (`set`); или обновить существующий инкрементально (`get` -> правки -> `set`). Ошибки валидации и stale-отчеты - машиночитаемые, пригодные для самостоятельной починки плана агентом.

## 9. Изменения в форке difit (точки подключения)

- Сервер: `GET/POST /api/walkthrough` в разрезе сессии (base:target:baseMode), поддержка stale-флагов на сниппетах, SSE-событие `walkthroughChanged`.
- Клиент: mount walkthrough-режима в App.tsx (одна точка), новые компоненты в отдельной директории (страница плана, WalkthroughSnippet, заглушка stale, баннер), утилита slice chunk.
- Общее: модуль валидации плана - пакет воркспейса `plan-schema` (используется сервером форка и оберткой).

## Отложенное (вне MVP)

- Опциональное поле `group` у страницы для группировки в UI - добавлять только при реальной необходимости (обратно-совместимо в рамках schemaVersion 1).
- Инлайн-ссылка на код без рендера сниппета.
- Отметка "страница просмотрена"; персистентность позиции в плане.
