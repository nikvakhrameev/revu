# revu - обертка difit, дизайн-документ

Спецификация по итогам дизайн-интервью. Покрывает пять пунктов проекта (интеграция с Claude Code, стейт по ветке/задаче, рендер локальных MR, GitLab-синк, блокировка ожидания) и фичу walkthrough. Формат walkthrough-плана (schemaVersion 1, `difit-ref`, `#page:`) - в `walkthrough-plan-design.md`; здесь описана его интеграция в общую архитектуру. Инкрементальные поколения ревью (счетчик `generation`, дельты `--since`, ошибка `CURSOR_INVALID`) описаны в `incremental-generations.md` - тот документ является источником истины для этой фичи.

Имя проекта, бинаря и пакета - **revu**. Домашняя директория - `~/.revu/`.

## 1. Общая архитектура

Система состоит из четырех частей:

1. **Демон revu** - единственный долгоживущий процесс и единственный писатель во все состояние. Владеет инстансами difit, реестром задач, хранилищем, GitLab-синком и walkthrough-планами.
2. **Форк difit** - рендер-мишень. Изменения изолированы и включаются одним флагом `--managed`; без флага поведение ванильного difit не меняется.
3. **CLI revu** - тонкие HTTP-клиенты к демону. Единственный бинарь, который ставится наружу.
4. **Скиллы агента** - два скилла для Claude Code поверх CLI.

### Репозиторий и дистрибуция

Стек: Node/TS. Один pnpm-монорепозиторий, корень - только workspace-мета:

```
packages/difit         форк difit; живет как git subtree, upstream подтягивается
                       `git subtree pull --squash`; бинарь не попадает в PATH и не публикуется
packages/revu          CLI + демон, один пакет, один бинарь `revu`
packages/plan-schema   валидация walkthrough-плана + общие типы; зависимость и форка, и revu
                       (у форка ровно одна новая workspace-зависимость в package.json -
                       минимальная поверхность конфликтов при subtree pull)
skills/                два скилла для Claude Code (в корне, как у самого difit)
```

Обертка импортирует модули форка напрямую (`git-diff.ts` для паритета диффа). Дистрибуция MVP - без публикации в npm: клон репо, `pnpm install && pnpm build`, затем `pnpm link --global` для `packages/revu`.

Ключевой инвариант: **ревьюится только закоммиченный код.** Working/staged/dot-режимы difit через обертку недоступны. Все ревью - фиксированные пары SHA (SPECIFIC-режим difit): файловый вотчинг всегда выключен, live-reload не участвует, обновление диффа возможно только рестартом инстанса.

difit в этой схеме stateless по комментариям и плану: источник правды - хранилище демона.

## 2. Демон revu

### Жизненный цикл

`revu daemon up` по умолчанию детачится (по образцу `difit --background`: спавн detached-процесса, IPC-handshake готовности, unref) и печатает JSON `{port, pid}`; флаг `--foreground` - для отладки. Останов - `daemon stop`, статус - `daemon status`. Логи демона - `~/.revu/daemon.log`.

Единственность экземпляра - биндинг порта: порт занят нашим демоном (подтверждается `GET /api/status`) - «уже запущен», не ошибка; занят чужим процессом - ошибка. Автостарта по требованию в MVP нет; скилл агента при недоступном демоне просит пользователя выполнить `revu daemon up`.

### Порты и конфиг

Демон - фиксированный порт **7388** (REVU на телефонной клавиатуре). Инстансы difit - диапазон **7400-7463** (64 параллельные задачи). Диапазон намеренно далеко от 4966: ванильный difit, запущенный руками, не столкнется с нашими портами.

Конфиг - `~/.revu/config.json`, все поля опциональны: `daemonPort`, `instancePorts {from, to}`, путь к `glab`.

Транспорт CLI -> демон: localhost HTTP, без аутентификации - модель угроз та же, что у самого difit (localhost-only).

### HTTP API демона

RPC-стиль, эндпоинты зеркалят команды CLI 1:1 (каждая команда - один вызов):

```
POST /api/review/start | stop | refresh     GET /api/review/list
GET  /api/review/wait                       (long-poll, см. ниже)
POST /api/comment/add                       GET /api/comment/get
POST /api/sync/pull | push
GET/PUT /api/plan                           POST /api/plan/check
GET  /api/status                            POST /api/shutdown
```

Ошибки: HTTP-статус + `{error: {code, message, details?}}`; коды - закрытый enum в общих типах (`DIRTY_WORKTREE`, `PORT_TAKEN`, `DAEMON_UNREACHABLE`, `TASK_NOT_FOUND`, `PLAN_VALIDATION_FAILED`, ...). CLI печатает тот же JSON в stderr и мапит ошибки в exit-коды.

Ожидание завершения ревью - long-poll: `GET /api/review/wait?timeoutMs=55000`, демон держит запрос до Finish либо отвечает `{status: "pending"}` по таймауту, CLI молча перезапрашивает. При недоступности демона - несколько ретраев, затем machine-readable ошибка.

### Инстансы difit

Демон спавнит форк detached-процессом со stdio `ignore`, флаги `--managed --keep-alive --no-open` (`--open` опционально пробрасывается из команды пользователя). Stdout-контракт difit не используется вообще: вся связь - HTTP API инстанса + SSE `/api/watch`. Готовность и принадлежность инстанса проверяются через `GET /api/instance-info`.

Порт инстанса выбирается как следующий свободный из диапазона и **закрепляется за задачей** в `meta.json`. Дальше порт липкий: тот же порт при каждом запуске ревью этой задачи, что сохраняет стабильный origin для localStorage браузера (viewed-файлы). Если закрепленный порт занят чужим процессом - ошибка запуска, никакого молчаливого сдвига. Авто-инкремент порта в форке под `--managed` отключен.

### Реконсиляция после рестарта демона

Detached-дети переживают смерть демона. При старте демон проходит по реестру и для каждой записи проверяет два условия: pid жив И `GET /api/instance-info` на записанном порту отвечает нашими `{repositoryId, base, target, startedBy: "wrapper", taskKey}`. Мертвые записи вычищаются, живые дети переподхватываются (ре-подписка на SSE).

## 3. Модель задач и жизненный цикл ревью

### Ключ задачи

`repositoryId` (sha256 абсолютного пути git-root - тот же, что считает difit) + source-ветка + base-ветка. GitLab MR ложится на этот ключ естественно (source + target branch). Внешний идентификатор (Jira и т.п.) - опциональное метаполе, не часть ключа.

Произвольные пары коммитов (`review start <shaA> <shaB>`) - эфемерные ревью: живут в реестре демона, но не персистятся как задачи.

### `review start` (идемпотентный)

1. Если в реестре есть живой инстанс задачи - вернуть его URL/port, не ошибка.
2. Проверка актуальности: сверить head source-ветки (для MR-задач - `head_sha` через GitLab API) с ревизиями, на которых поднят инстанс. Разошлось - рестарт инстанса на том же порту с ре-инжектом тредов из снапшота. Тот же механизм доступен явной командой `review refresh`.
3. Проверка чистоты: если source-ветка задачи - текущая checked-out ветка и worktree грязный (включая untracked) - жесткая machine-readable ошибка; обход `--allow-dirty`. Для MR-задач, поднимаемых по SHA из `diff_refs`, проверка не выполняется.
4. Подъем инстанса difit на паре SHA, инжект тредов задачи (`POST /api/comment-imports`) и push плана (`POST /api/walkthrough`), если они есть в хранилище.

### Завершение ревью

Сигнал "пользователь закончил" - кнопка **Finish review** в UI форка (основной UX), эмитящая SSE-событие; запасной канал - команда обертки. Закрытие вкладки ничего не завершает (с `--keep-alive` инстанс живет).

По Finish демон снимает финальный снапшот тредов, гасит ребенка difit; порт остается закрепленным за задачей.

## 4. Хранилище состояния

Глобально в home, вне репозитория:

```
~/.revu/state/<repositoryId>/<taskKeyHash>/
  meta.json       ключ задачи, port, pid, ревизии на момент запуска, внешний id
  threads.json    последний снапшот {version, threads, capturedAt, headSha}
  resolved.json   архив закрытых тредов с таймстемпами
  plan.json       walkthrough-план + хэши сниппетов
  staging.json    очередь comment add, принятых при мертвом инстансе
  sync.json       состояние GitLab-синка: publishState тредов, маппинг messageId <-> noteId
```

Конвенции хранилища: демон - единственный читатель и писатель (CLI ходит только через HTTP, файлы напрямую не трогает); атомарная запись tmp+rename (как user-config в difit); в каждом файле поле `schemaVersion`; схемы описаны и валидируются zod-ом в коде демона.

### Поток комментариев

- **Снапшоты:** демон подписан на SSE `/api/watch` инстанса; на каждое `commentsChanged` - `GET /api/comments-json?base&target&baseMode` с явными параметрами сессии и запись в `threads.json`. Подкоманда `difit comment` самого difit не используется (она не умеет выбирать сессию).
- **Закрытые треды:** при снапшоте демон диффит старый и новый списки; исчезнувшие треды перекладываются в `resolved.json`.
- **Ре-инжект после рестарта:** наивный, по сохраненным якорям (filePath + side + line). `codeSnapshot` обязателен во всех снапшотах и импортах - родной механизм difit (`isThreadOutdated`) сравнит снапшот с текущими строками и сам повесит outdated-бейдж на уехавшие треды.
- **localStorage браузера в контуре комментариев не участвует:** под `--managed` клиент difit не читает и не пишет треды в localStorage (см. раздел 7). Viewed-файлы остаются в localStorage как есть.

## 5. GitLab-синк

### Источник диффа

Только локальные ревизии, stdin-режим difit не используется. Демон берет `diff_refs` MR-а из API (`base_sha`, `head_sha`), делает fetch (`refs/merge-requests/<iid>/head` + target-ветка), и запускает difit ровно на паре `head_sha` x `base_sha` без `--merge-base` (base_sha уже merge-base). Это гарантирует построчный паритет с диффом на странице MR; локальное состояние веток в MR-ревью не участвует.

### Pull (GitLab -> difit)

Импортируются только unresolved-дискуссии с валидной позицией на текущей версии диффа; resolved, outdated и общие (непозиционные) комментарии MR пропускаются - зеркально поведению родного `--pr` для GitHub. Маппинг: дискуссия -> тред (`id` = id дискуссии GitLab, дедупликация), notes -> корень + реплаи. Pull пропускает дискуссии, чей id числится в состоянии `resolved-local` (тумбстоун).

### Push (difit -> GitLab)

`sync push` за один вызов приводит системы к сходимости: публикует все еще не опубликованные треды как дискуссии и закрывает (resolve) на GitLab все `resolved-local` с известным `gitlabDiscussionId`.

### State machine треда (в `sync.json`)

`origin`: local | agent | gitlab. `publishState`: `local-only -> published`; `resolved-local -> resolved-synced` (тред лег в resolved.json, дискуссия закрыта push-ем).

### Реплаи

Полный инкрементальный синк в обе стороны с таблицей маппинга `messageId <-> noteId`: pull дописывает новые notes реплаями в существующий тред (дедуп по id note), push публикует новые локальные messages как notes.

### Режим синка и клиент

Только явные команды `sync pull` / `sync push` (плюс опция автопулла при `review start` MR-задачи). Никакого фонового автосинка. Клиент - бинарь `glab` (`glab api` для дискуссий), аутентификация через `glab auth login`, собственного управления токенами у обертки нет; self-hosted GitLab - через конфиг glab.

Родной `--pr` (GitHub) остается фичей ванильного форка вне ключей задач; обертка его не оборачивает и не ломает.

## 6. Walkthrough

Формат плана - по `walkthrough-plan-design.md`: JSON-конверт schemaVersion 1, тело страниц - Markdown, `difit-ref`-блоки с YAML-телом (file / lines / side), `#page:`-ссылки, slug-id страниц. Синтаксис v1 зафиксирован там же. Единый модуль валидации - пакет `plan-schema`, используется командой `plan validate` и сервером форка при `POST /api/walkthrough`.

### Доставка

Единственный путь - runtime: `POST /api/walkthrough` (демон), `GET /api/walkthrough` (клиент), SSE-событие `walkthroughChanged` в существующий канал `/api/watch`. Стартового флага предзагрузки нет. Демон пушит план сразу после подъема инстанса и после каждого `plan set`.

### Хэши и stale

Хэш сниппета = sha256 точного диапазона строк блоба на закрепленной ревизии: `side: new` -> строки `head_sha:path`, `side: old` -> `base_sha:path`. Настройки рендера (context lines, whitespace) на хэш не влияют. `side` в `difit-ref` опционален, по умолчанию `new`; для неизмененных файлов валидатор разрешает ссылку без side.

Обертка считает хэши тем же кодом, что difit режет дифф (импорт `git-diff.ts` форка) - паритет по построению. Межзапусковой stale-контур: `plan check` / `plan set` пересчитывают хэши против текущих закрепленных ревизий и помечают разошедшиеся сниппеты stale-флагом при заливке в difit. Внутрисессионная ревалидация клиентом сохранена только как защита от рассинхрона при `plan set` на лету (дифф внутри сессии неизменен - live-reload в managed-режиме не бывает).

### Комментарии и позиция

Комментирование в сниппетах разрешено везде, включая blob-синтезированные строки неизмененного кода. Известное поведение MVP: тред с якорем вне hunk-ов в полном диффе инлайн не виден (доступен через список комментариев и после разворота контекста); в comments-json, снапшоты и GitLab-синк такие треды попадают полноценно.

Позиция в плане (страница + скролл) в MVP не персистится: план всегда открывается с первой страницы, позиция живет только в стейте открытой вкладки.

## 7. Форк difit - полный список инкрементов

Все клиентские/серверные изменения включаются одним флагом `--managed` (сервер отдает его клиенту в `/api/diff`); без флага - ванильное поведение.

| Инкремент | Что делает |
|---|---|
| externalCommentAuthority | клиент не читает и не пишет треды в localStorage; комментарии - только сервер |
| скрытие RevisionSelector | смена ревизий на лету в managed-инстансе невозможна |
| `GET /api/instance-info` | `{repositoryId, base, target, baseMode, startedBy, taskKey}` - идентификация инстанса демоном |
| кнопка Finish review | UI-кнопка + SSE-событие завершения ревью |
| `GET/POST /api/walkthrough` + SSE `walkthroughChanged` | план в разрезе сессии, stale-флаги на сниппетах |
| walkthrough-режим клиента | страницы плана, `WalkthroughSnippet` (slice chunk -> DiffChunk/SideBySideDiffChunk), blob-сниппеты через машинерию useExpandedLines, заглушки stale, баннер |
| отключение авто-инкремента порта | занятый порт - ошибка, портами управляет демон |

## 8. CLI revu

Все команды - HTTP-клиенты к демону (см. раздел 2, HTTP API). Вывод по умолчанию JSON, `--format text` для человека. Ошибки - тот же machine-readable JSON, что отдает демон, в stderr + exit-код.

```
revu daemon up [--foreground] | stop | status

revu review run <source> [base]     блокирующая: идемпотентный start + long-poll
                                    ожидание Finish + финальный снапшот тредов в stdout
revu review start | wait | stop | refresh | list
                                    неблокирующие примитивы того же цикла

revu comment add [json] --task      живой инстанс -> POST /api/comment-imports
                                    (с явными base&target из meta); мертвый ->
                                    staging-очередь до следующего start
revu comment get --task             threads.json + resolved.json из хранилища
                                    (история и полный контекст для агента)

revu sync pull | push --task        GitLab-синк (раздел 5)

revu plan validate <file>           dry-run валидация без записи
revu plan get | set | check --task  план: чтение со stale-флагами, установка
                                    (валидация + хэши + push в живой инстанс),
                                    проверка актуальности
```

`review run` сохраняет проверенную на агентах ментальную модель родного скилла difit ("запусти и жди вывода"), но без гонок stdout-контракта: финальный снапшот - структурный JSON из хранилища.

## 9. Интеграция с Claude Code

MCP в MVP нет: только CLI + скиллы, Claude Code работает через bash. MCP-сервер при необходимости добавляется позже как тонкий адаптер над HTTP API демона без изменений архитектуры.

Обход обертки предотвращен конструкцией: наружу ставится только бинарь `revu`, бинарь форка недоступен в PATH, родные скиллы difit не устанавливаются.

Два скилла (зеркально паре скиллов difit):

1. **request-review** - "попроси у пользователя ревью": коммит перед запросом (инвариант "только закоммиченный код"), `revu review run`, интерпретация "Finish без комментариев = замечаний нет, не перезапускать", цикл починки плана через `revu plan validate` до чистой валидации.
2. **review-code** - "отревьюй сам и покажи находки": агент ревьюит код и заливает результат через `revu comment add` и `revu plan set`.

В оба скилла зашиты: security-guardrail difit (не копировать секреты/токены/ключи из диффа в тела комментариев и аргументы команд) и правило "демон не отвечает -> попросить пользователя выполнить `revu daemon up`".

## 10. Пост-MVP и открытые пункты

- **Plan-only review** (первое расширение): ревью walkthrough-плана до написания кода - пустая сессия (base == target == HEAD) под `--managed`, страницы плана + blob-сниппеты + комментарии; все решения MVP с этим совместимы.
- Ре-анкоринг якорей тредов после новых коммитов (ремап через diff `headSha` снапшота -> новый head; задел - `headSha` в `threads.json`).
- GitHub-синк на равных с GitLab (state machine и маппинг из раздела 5 переиспользуются).
- Выборочный push (`sync push --threads <id...>`).
- Общие (непозиционные) комментарии MR - кандидат на отображение страницей walkthrough-плана.
- Авто-разворот контекста до якоря вне hunk-ов при переходе из списка комментариев.
- Персистентность позиции в плане; отметка "страница просмотрена".
- Вотчинг ref-ов веток в форке (авто-детект нового head вместо проверки на start).
- MCP-адаптер над HTTP API демона.
- Публикация в npm (сейчас - pnpm link из клона репо).
